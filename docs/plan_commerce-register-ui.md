# EC検索面の発信元登録UI補完（plan: nope-commerce-register-ui）

楽天市場・Yahoo!ショッピング・Amazonは、保存済みブロック値を検索カードへ適用する機能だけが実装され、利用者が画面からショップ／出品者を登録する入口が欠けていた。旧smokeはstorageへ値を直接投入したため、この欠陥を見逃した。

本工程では3サイトをNopeの正式スコープとして、検索結果から発信元を登録し、対象一致・即時ブロック・解除復元まで通る利用者導線を補完する。工程正本はLattice storeのplan `nope-commerce-register-ui`とし、本書は目的・受入境界の説明だけを担う。

## 成功条件

1. 楽天市場の解決可能な商品カードに「このショップをブロック」が表示される
2. Yahoo!ショッピングの解決可能な商品カードに「このショップをブロック」が表示される
3. Amazonの販売者を解決できた商品カードに「この出品者をブロック」が表示される。Amazon直販など販売者不在カードには誤った登録UIを出さない
4. 登録するIDと表示名は各adapterが解決した安定値を使い、押したカードとpopup登録対象が一致する
5. 操作直後に同じ発信元の商品がブロックされ、プレースホルダーとpopupの双方から解除・復元できる
6. YouTubeは従来どおり「このチャンネルをブロック」と表示され、既存7サイトの挙動を壊さない
7. 自動テスト、再梱包、stable unpackedとの一致を確認後、オーナーの通常Chromeで3サイトを1つずつ受入する

## タスク

### crui-contract-tests — 登録UI契約と失敗テスト

storage直投入ではなく、カードに登録ボタンが生成され、clickでadapterのID・表示名が保存され、解除まで到達する契約をテストで固定する。サイト固有名詞（ショップ／出品者／チャンネル）とAmazon販売者不在の負契約も、実装前に赤くなるテストとして追加する。

### crui-implementation — 共通エンジンと3adapterの登録UI実装

`content-search.js`の登録UIへadapter指定の発信元種別を渡し、ボタン文言・識別子解決失敗表示をサイトに合わせる。楽天市場・Yahoo!ショッピングはショップ、Amazonは出品者として登録を有効化する。Amazon販売者不在カードは現状どおり対象外とする。

### crui-package-smoke — 再梱包とオーナー実Chrome受入

関連テストと全テストを実行し、ZIPとstable unpackedを再生成・比較する。オーナーの通常Chromeで楽天市場、Yahoo!ショッピング、Amazonを順に確認し、各サイトでボタン表示、対象一致、ブロック、解除復元を合格させる。Amazonは販売者が存在するマーケットプレイス商品を使う。

### crui-terminal-audit — 別席による終端監査

実装席とは別の円卓席が、3サイトすべてに登録入口があること、storage直投入だけの偽受入でないこと、Amazon直販を販売者として捏造しないこと、サイト固有文言、配布物、オーナー実Chrome証跡を反証する。

## 依存

`crui-contract-tests` → `crui-implementation` → `crui-package-smoke` → `crui-terminal-audit`。安全網を先に固定し、共通エンジンとadapter設定は同じ利用者導線として一受入単位で実装するため直列化する。

## この工程の外にあるもの

- 商品単位・価格帯・カテゴリ単位のブロック
- Amazon直販を架空の出品者IDでブロックすること
- 検索以外の商品詳細・ランキング・レコメンド面への対象拡張
- Chrome Web Storeへの提出・支払い・公開

## 既知の罠

- storageへ完成済み値を直接入れて非表示だけを見ると、登録UI欠落を再び見逃す
- 共通エンジンの現行文言は「チャンネル」に固定されており、そのまま3adapterを有効化すると誤表示になる
- Amazon検索結果の多くはAmazon直販で販売者が存在しない。ボタン0件だけでは壊れと断定できないため、販売者解決済みカードと不在カードを分けて検証する
- サイト管理DOM内へのボタン挿入は再描画で消える可能性がある。自動fixtureだけでなく通常Chromeの実ページで位置と存続を確認する
